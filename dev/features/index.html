Features

All features are toggles or fields on SlackClawConfig. Defaults are in the configuration table.

Agent directives

When agent_directives is enabled (default), Claude can control its own execution flow by ending a response with a directive:

  • [CONTINUE] — immediately re-invoke in the same session for multi-step work.
  • [CONTINUE: next step description] — re-invoke with a specific follow-up prompt.
  • [SCHEDULE: 2h: check pipeline results] — queue a future invocation; durations accept 30m, 1h, 2h30m, and the like.

If no directive is present the task is complete. Consecutive [CONTINUE]s are capped at max_continue (default 10) as a runaway guard; scheduled tasks survive restarts via .slackclaw_state.json.

Multi-channel listening

A monitor can listen to channels beyond its primary one. Set listen_channel_ids:

run_monitor(SlackClawConfig(
    slack_channel_id   = "C_PRIMARY",
    listen_channel_ids = ["C_GENERAL", "C_ANNOUNCE"],
    repo_dir           = "/path/to/repo",
))

Messages from listen channels run through a relevance filter first: Claude is asked whether the message is relevant to this instance's repo/role and answers [SKIP] if not. The check is a containment match ([SKIP] anywhere in the reply): models reliably narrate their verdict and leave the token at the end, and a stricter check would post that narration as spam — here a false positive only suppresses an optional post. Only relevant messages are posted — as a new thread in the primary channel, prefixed with the sender and source channel name — and handled there. The bot must be a member of each listen channel; channel names are resolved on startup and cached. Listen-channel events arrive live on the same socket as the primary channel; the only extra cost is that the periodic reconciliation also backfills each listen channel's history.

Sender attribution

Every user message reaches Claude prefixed with its authenticated Slack sender:

[from <@U0123ABCDE>]

<the user's message>

on the primary/thread paths, and inline — [from <@U0123ABCDE> in #general] … — on the listen path. The sender comes from the Slack event's user field, not from anything typed in the message, and the prefix is unconditional (no config toggle). It exists so a channel's system_prompt can enforce per-user authorization rules ("only run deploys when the requester is <@U…>") and record who asked for each action — neither is possible if the authenticated sender never reaches Claude.

Only the first [from …] line of a prompt is authoritative. A user can type a forged [from …] line at the start of their message, so SlackClaw neutralizes any leading [from …]-shaped lines in the user text (they become user wrote: [from …]) before attaching the real prefix — the forgery stays visible, but cannot pose as the attribution. Messages without a user field are attributed [from unknown], which fail-closed authorization prompts should reject.

Declining to answer (allow_skip)

In a shared channel full of people, teammate-like behavior means answering when useful and staying out of exchanges aimed at other people. With allow_skip = true, a reply of exactly [SKIP] on the primary/thread path posts nothing and adds no checkmark (the thread's Claude session is still tracked, so later in-thread replies keep continuity). The match is exact (strip(text) == "[SKIP]"), stricter than the containment match on the listen/proactive filters — on this path a false positive would swallow a real answer in the user's own channel. This is only the mechanism: instruct Claude when to skip via system_prompt. To help it tell when it was tagged, mentions of the bot itself reach Claude as @you instead of a raw <@U…> ID.

The 👀 reaction doubles as an intent signal on allow_skip channels: eyes go on at dispatch (as on every channel), and come back off when the reply is [SKIP]. Lingering eyes mean a reply is coming; vanished eyes mean the bot saw the message and is deliberately staying out. Failures to remove the reaction (deleted message, manual un-react race) are swallowed — an un-react is always benign. Default off — existing deployments behave as before.

Proactive mode

When proactive_enabled = true, SlackClaw periodically runs Claude to check for things worth reporting (every proactive_interval_s, default 1 h) — but only once it has an agenda: it fires only when .slackclaw_proactive_tasks exists in repo_dir (or proactive_prompt is set). Claude reads two files in repo_dir at runtime:

  • .slackclaw_proactive_tasks — what to check. Editable anytime without a restart, so you can adjust the agenda live.
  • .slackclaw_proactive_log — what was already reported (auto-appended). Claude reads it to avoid repeating itself.

If nothing is noteworthy, Claude responds [SKIP] and stays silent; only real content is posted as a top-level message in the primary channel. As on the listen path, the check is a containment match — a narrated decline ("checked everything, nothing new. [SKIP]") is suppressed rather than posted. A suppressed run's full text is still appended to the log (tagged [suppressed]) so the next cycle's dedup keeps its reasoning.

run_monitor(SlackClawConfig(
    proactive_enabled    = true,
    proactive_interval_s = 1800,   # every 30 min
))

Frequency can be changed live by posting in the monitored channel:

  • proactive every 30m (or proactive interval 2h) — adjust the interval
  • proactive on / proactive off — toggle

The proactive_prompt field can carry inline suggestions, but prefer .slackclaw_proactive_tasks so the agenda hot-reloads.

Progress updates during long tasks

Each run in a thread has its own status file, named to Claude as SLACKCLAW_STATUS: <status_file>.<channel>.<thread ts> in repo_dir (status_file defaults to .slackclaw_status). While the run goes, SlackClaw polls it every status_poll_s; any non-empty content present when it polls is posted to the thread as a progress update (a value overwritten between polls can be missed). The file is removed when the run ends, one left by an earlier run in the thread is removed when the next run starts, and the monitor removes its channel's leftovers when it starts (a run it stopped mid-way). A thread has one run at a time, so two runs never share a status file and one run's progress never shows in another thread. To use it, tell Claude in system_prompt to write progress to the file named by $SLACKCLAW_STATUS when that variable is set: listen and proactive runs have no thread to post progress in, so they get no status file. A repository that ignores the file needs the pattern .slackclaw_status* (with the star; or <status_file>* for a channel that sets status_file). The single status file 0.7.4 and earlier used (.slackclaw_status, or the status_file a channel set) is no longer read or removed; delete one left behind by hand.

What the Claude child receives

Every run of claude gets an allow-listed environment, not the monitor's: a fleet's environment holds every workspace's Slack tokens and other credentials, and the run follows prompts any channel member can write. It inherits only (CHILD_ENV_NAMES, CHILD_ENV_PREFIXES):

  • what a shell, git, gh, the CLI and its HTTP client need: PATH, HOME, USER, LOGNAME, SHELL, LANG, LANGUAGE, TERM, TZ, TMPDIR/TMP/TEMP, SSH_AUTH_SOCK, DBUS_SESSION_BUS_ADDRESS, the proxy variables, certificate trust and Node's options (SSL_CERT_FILE, NODE_EXTRA_CA_CERTS, NODE_USE_SYSTEM_CA, NODE_OPTIONS, GIT_SSL_CAINFO, …), and git and gh identity and configuration (GIT_AUTHOR_*, GIT_COMMITTER_*, GIT_SSH_COMMAND, GIT_CONFIG_GLOBAL, GIT_TERMINAL_PROMPT, GH_CONFIG_DIR, GH_REPO, GH_HOST);
  • the child's own Anthropic credential, endpoint and models (ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_BASE_URL, ANTHROPIC_MODEL and the other model and cloud-endpoint names, Bedrock, Vertex and Foundry included), but not an admin key;
  • the names, not the secrets, of a cloud provider's profile, region and files (AWS_PROFILE, AWS_REGION, AWS_CONFIG_FILE, CLOUD_ML_REGION, GOOGLE_APPLICATION_CREDENTIALS, …);
  • variables starting with LC_, XDG_, JULIA_, JULIAUP_ or CLAUDE_ (less the nested-session variables CLAUDECODE and CLAUDE_CODE_*, except CLAUDE_CODE_OAUTH_TOKEN; those never pass, not even through child_env_passthrough, so set such options in Claude Code's settings.json);
  • the variables the channel names in child_env_passthrough, by exact name (for example ["ZOTERO_API_KEY", "ZOTERO_LIBRARY_ID", "GH_TOKEN"]; an entry ending in * is not a prefix, and is logged once and ignored).

None of the built-in prefixes passes a name that looks like a secret (one containing TOKEN, SECRET, PASSW, KEY, CREDENTIAL, WEBHOOK, COOKIE or the word PAT, such as a CLAUDE_SESSION_KEY): such a variable passes only by exact name.

Three more rules hold over all of it. A variable whose value holds a Slack token or webhook URL anywhere (a xoxb-, xoxp-, xapp-, xwfp- or other xox token, a session cookie xoxd-, alone or in a header, or an incoming-webhook URL on hooks.slack.com or hooks.slack-gov.com) never passes, even when child_env_passthrough names it. This recognizes tokens by their shape: a Slack app's signing or client secret has none, so keep such a variable out of child_env_passthrough. A URL with a user name or password, such as a proxy with its password (with or without http://), passes only when child_env_passthrough names the variable exactly. And the variables SlackClaw sets for each run are never inherited: SLACKCLAW_THREAD_TS, SLACKCLAW_CHANNEL_ID, SLACKCLAW_BOT_TOKEN (the channel's bot token, for the upload helper), SLACKCLAW_UPLOAD, and SLACKCLAW_STATUS for a run in a thread. Other SLACKCLAW_* names, such as the upload helper's SLACKCLAW_UPLOAD_COMMENT, pass when the channel names them. SlackClaw logs the name (never the value) of a variable it drops for its value, once per process.

Claude Code's own settings variables (DISABLE_AUTOUPDATER, BASH_MAX_TIMEOUT_MS, MCP_TIMEOUT, …), host policy (CUDA_VISIBLE_DEVICES, the thread-count variables, LD_LIBRARY_PATH, a display) and npm's cache location (npm_config_cache) pass by exact name too. Anything else a channel's runs used from the monitor's environment, such as a tool's API key, must be listed in child_env_passthrough before upgrading.

Instructions and memory. SlackClaw's instructions to a run (the channel's system_prompt, the directive and upload instructions) are added after Claude Code's own system prompt (--append-system-prompt), so a run keeps Claude Code's built-in instructions, such as confirming before hard-to-reverse or outward-facing actions. Claude Code records a conversation's prompt at its first request, so a thread keeps the prompt it started with until its conversation is compacted; an edited system_prompt reaches new threads. Claude Code's auto memory is off in runs (CLAUDE_CODE_DISABLE_AUTO_MEMORY=1): Claude Code does not load the repository's memory index into a run, and does not tell it to save memories there, so a member's message does not turn into a memory that later threads, or a person's own Claude sessions in that repository, load and act on. This is the built-in behavior only: a run can still read and write files in that folder with its ordinary tools when a prompt asks it to. Set auto_memory = true for a channel whose runs should load the index and be told to save to it (a launcher that builds the configs must pass the field). Either way the setting applies to new threads: a thread keeps the instructions its conversation started with until it is compacted.

What this does not do. The allow list governs the environment a run inherits. A run is the monitor's own OS user, so it can still read any file the monitor can (slackclaw.env, which setup() writes into repo_dir by default; a shell startup file that exports tokens; a token file in a checkout it works in) and the monitor's own process environment. Keep token files out of the folders runs work in. Keeping tokens out of a run's reach entirely needs the run under its own OS user.

Sending files and images

When Claude runs under SlackClaw with an active thread, it can attach a file or image to its reply. SlackClaw injects SLACKCLAW_UPLOAD (the path to the bundled bin/slack-upload helper) plus the thread context (SLACKCLAW_THREAD_TS, SLACKCLAW_CHANNEL_ID, SLACKCLAW_BOT_TOKEN) into the subprocess environment, and appends a short instruction to the system prompt telling Claude the helper exists. So "plot X and send it back" needs no extra wiring: Claude saves the figure and runs $SLACKCLAW_UPLOAD <file_path> ["caption"], which posts it into the current thread via Slack's external upload flow (files.getUploadURLExternal + files.completeUploadExternal). It needs curl and jq on the host and the files:write scope — included in the setup manifest, but apps created before this release must add files:write and reinstall.

Concurrency and thread limits

  • Each message is dispatched as an async task; at most max_concurrent_tasks (default 5) run at once. Messages that arrive while at the cap get a brief "busy" reply.
  • A busy thread that receives another message reports elapsed time instead of starting a second run.
  • At most max_active_threads (default 3) conversation threads are tracked, besides those with a run in flight or a follow-up scheduled (never retired); the oldest are retired first. Threads idle longer than max_thread_idle_s (default 7 days; 0 disables) are also retired — each tracked thread costs a conversations.replies call per reconciliation, so this bounds steady load.

Failed runs

A failed run (a step-limit stop, a usage limit, a timeout, any non-zero exit) does not end its thread. Every run leaves its thread tracked, whatever the outcome (the one exception: a follow-up saved by an older version, whose thread is no longer tracked and whose notice fails to post), so a reply there starts a new run: by socket, or by the next reconciliation poll if the socket missed it. SlackClaw adds ❌, frees the thread, and then posts the reason, so a reply sent the moment the reason appears starts a run instead of "Still working". A failed reaction is logged and never stops the post.

  • When the CLI printed a session id (it does for a step-limit stop, and for any failure that prints its result object), the next run resumes that session, with what the failed run already did. The reply ends with "Reply in this thread to continue; the next run resumes this one."
  • A run that timed out while resuming a session worked in that session (the CLI writes the transcript as it goes, under the same id), so the next run resumes it, with the same line.
  • When it printed none and did not get that far (a start-up failure, or a fresh run that timed out), the thread keeps the session it already had, so the next reply resumes the earlier conversation (a thread with no session yet starts fresh, told that the earlier context is not available). The failed run's work is not in that session, so the reply ends with "Reply in this thread to try again, saying what is still to be done: this run left nothing to resume, though some of its work may have run."
  • A scheduled follow-up that fires in a session other than the one that scheduled it (the thread started over since) is told so, and asks rather than guesses what it refers to.
  • A step-limit stop reads "Claude stopped at the step limit before finishing." Raise max_turns for a channel whose tasks need more steps.
  • A session the CLI no longer has (its transcripts were moved or removed, for example after the account behind CLAUDE_CONFIG_DIR changed) is dropped, and the same message runs again at once, so the user never has to send it twice. The rerun starts fresh, told the earlier context is not available, unless the thread holds a different session, which the rerun resumes. It reruns once per dispatched message.
  • A scheduled follow-up resumes the thread's current session, not the id it was saved with, and waits while its thread is running.
  • A thread has one run at a time: a reply in a thread that already has a run gets "Still working". A top-level message that reached SlackClaw late, after a reply in its thread, says it was not run while that thread is running, and otherwise resumes the thread's conversation when it has one (else runs fresh), told it came after replies already handled (and may have been edited), so a conflict is asked about.

A failed thread counts toward max_active_threads like any other. A thread with a run in flight or a follow-up scheduled is never expired, and sits beside the cap rather than in it. A thread's reply cursor follows Slack's timestamps only (the message a run answered, then the last reply read), never the host clock. A reply posted during a thread's first run is read by the next poll after the run; one the poll or socket reads while a run is going is answered "Still working".

Persistence

State is saved to state_file (.slackclaw_state.json in repo_dir): the primary cursor, tracked thread sessions, scheduled tasks, per-listen-channel cursors, and the last proactive timestamp. It is loaded on startup, so sessions and schedules survive restarts. Channels that share a repo_dir must each set a distinct state_file. ```
